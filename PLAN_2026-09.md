## Chunk 1 — Fix the People/Team ARR calculation bug

**Size:** small, backend-only.

**Root cause:** `app.py`'s `list_reps` (`/api/reps`) has an `arr_total`
subquery (around line 75) that sums *all* `closed_deals` rows for a rep with
no `sales_stage` filter:

```sql
SELECT COALESCE(SUM(amount),0) FROM closed_deals cd WHERE cd.se_rep_id = r.id
```

Since commit `ed4923f` ("Sync closed_deals with full Won+Lost dataset"),
`closed_deals` holds both Closed/Won and Closed/Lost rows (see README.md
"Data model" and CLAUDE.md's MCP-sync section, both of which already
document this). That commit correctly fixed `/api/closed-deals/summary`'s
WHERE clause to account for the mixed data, but never applied the same fix
to this separate, undocumented `arr_total` subquery. Result: `arr_total`
double-counts Lost-deal amounts as if they were revenue, making reps look
wildly over target (confirmed live: Sean Keleher showed `$24.97M` against a
`$2.5M` target instead of the correct `$1.10M`, ~44% of target).

**Tasks:**
1. Add `AND cd.sales_stage = '10 - Closed/Won'` to the `arr_total` subquery
   in `list_reps`.
2. Audit the adjacent `tech_forecast_arr` computation in the same query
   block — confirm it's unaffected (it sums `tech_forecast_deals`, not
   `closed_deals`) and leave a one-line note if so.
3. Add a line to CLAUDE.md's MCP-sync section documenting that `arr_total`
   must stay Won-only now that `closed_deals` is mixed — this is the
   documentation gap that let the bug ship unnoticed.
4. Verify against live data for Sean Keleher, Rishika, Nic, Valentin, and
   Jordan Taylor — confirm `arr_total` now matches `arr_total_won_only` and
   the Team/Person page progress bars look sane against `arr_target`.
5. Update README.md if the fix changes any documented behavior.

**Consumers to check post-fix:** `frontend/src/pages/Team.jsx` (`arrGoalBar`
call) and `frontend/src/pages/Person.jsx` (`arrGoalBar` call) — no code
changes expected there, just visual re-verification.

## Chunk 3 — Depth / "3D" styling pass

**Size:** medium, CSS-only, requires manual visual verification in both
light and dark theme.

**Context:** `frontend/src/style.css` already defines a depth-token system
(`--depth-raised`, `--depth-raised-hover`, `--depth-inset`,
`--depth-inset-focus`, `--glow-blue`, `--card-grad`) toggled per-theme via
the `body.light-mode` class, but it's underused — only `.card`/`.stat-card`
consume `--depth-raised`. Buttons have no shadow at all, `--depth-raised-hover`
is defined but never wired to anything, no `:active` pressed state exists
anywhere, and `.sidebar-btn`/`.tab-btn` are separate ad-hoc shadowless
styles outside the token system.

**Tasks:**
1. Give the base `.btn` a real raised box-shadow (using `--depth-raised`).
2. Wire `--depth-raised-hover` onto `.btn:hover` (currently defined, unused).
3. Add a genuine `:active` pressed state on buttons — inset shadow +
   slight `translateY` — there is none anywhere in the app today.
4. Extend the same raised/hover/active treatment to `.sidebar-btn` and
   `.tab-btn`, bringing them into the shared token system instead of their
   separate ad-hoc styles.
5. Strengthen `.card`/`.stat-card` shadow depth if needed for visual
   consistency with the new buttons.
6. Bring the shadowless outliers (`.slack-note`, `.toast`) into the token
   system too.
7. Verify visually in both dark mode and light mode (`body.light-mode`) —
   depth tokens are redefined per-theme, so both need a manual look.
8. No README/CLAUDE.md changes expected — pure visual styling, no behavior
   change.

## Chunk 4 — Dashboard overhaul (do last, largest chunk)

**Size:** large — split into 2-3 agents (backend, frontend, docs/verification).

**Intent (Claude Leroux, 2026-09-11):** the current Dashboard (current-quarter
SFDC pipeline table, filterable by quarter/stage/search, with POC/SE-Needed
flags) is no longer relevant. Replace it entirely with team-wide graphs and
visuals sourced from Technical Forecast data. Top level must show **no SE
names** — roll-up totals for the team only.

**Open decision — fiscal vs. calendar quarters:** the current Dashboard uses
calendar quarters (`app.py.current_quarter()`); Technical Forecast uses Okta
fiscal quarters (`tech_forecast_report.fiscal_quarter()`, FY starts Feb 1).
**Recommendation: standardize the new Dashboard on fiscal quarters** to match
Technical Forecast, since it's now sourcing from that data. Flagging this
here as the plan of record — revisit only if it turns out to be confusing
once built.

**Backend agent tasks:**
1. Add a time-series ARR-trend endpoint using the full
   `tech_forecast_snapshots` history (not just the most-recent diff that
   `build_weekly_deltas` produces) — needed for a trend-over-time chart.
2. Add/expose a clean, team-wide, SE-name-free per-stage funnel rollup
   (reuse `tech_forecast_report.build_breakdown()` where possible).
3. Add a quarter-over-quarter Tech Win comparison (reuse
   `tech_forecast_report.fiscal_quarter()` / `build_key_metrics()`).
4. Reuse `/api/closed-deals/summary`'s existing `team` object (already
   SE-name-free, already team-wide) rather than re-deriving it.

**Frontend agent tasks:**
1. Add a charting library — none exists yet in `frontend/package.json`
   (recommend `recharts`).
2. Fully replace `frontend/src/pages/Dashboard.jsx` — drop the current
   per-deal SFDC table (which shows `d.lead_se`, violating the
   no-names-at-top-level requirement) in favor of team-wide graphs/visuals:
   ARR trend, stage funnel, QoQ Tech Win comparison, key stat cards (reusing
   `build_key_metrics()`-shaped data).
3. Ensure nothing on the new Dashboard renders an individual SE name at the
   top level — only team-wide rollups.

**Docs/verification agent tasks:**
1. Update README.md's "Dashboard" bullet to describe the new, Technical-Forecast-sourced,
   team-wide view (replacing the current SFDC-table description).
2. Update CLAUDE.md if the fiscal-vs-calendar standardization introduces any
   new caller of `fiscal_quarter()` worth documenting alongside the existing
   "Fiscal quarters" section.
3. Manually verify the new Dashboard against live data, in both light and
   dark theme.
